  1. Export:  curl -H "Authorization: Bearer $AGENT_API_KEY" https://OLD_HOST/api/config/export > config.json
  2. Import:  curl -X POST -H "Authorization: Bearer $AGENT_API_KEY" \
                   -F "file=@config.json" https://NEW_HOST/api/config/import
  WARNING: import is destructive — it clears existing config before importing.

── Rollback Procedure ────────────────────────────────────────────────────────

export-config is a backup tool — it exports DB state to JSON files for safekeeping.
To export the current DB state:
  kubectl exec deployment/{{ include "coding-agent-automation.fullname" . }}-orchestrator -n {{ .Release.Namespace }} -- \
    dotnet CodingAgentWebUI.dll export-config --output /tmp/pipeline-export

Then copy out:
  kubectl cp {{ .Release.Namespace }}/$(kubectl get pod -l app.kubernetes.io/component=orchestrator -n {{ .Release.Namespace }} -o jsonpath='{.items[0].metadata.name}'):/tmp/pipeline-export ./pipeline-backup

To roll back to a previous version: restore from backup using the import endpoint (see First-Run above).

── Upgrade Notes ─────────────────────────────────────────────────────────────

Let in-flight work finish before upgrading — there is no drain hook. Jobs already
dispatched run to completion regardless, but new dispatch is paused during the
rollout. For zero downtime, wait until WorkItems reach terminal state, then upgrade.

Spec 043 changes (current):
  - Template validation in Settings is unavailable after 043 until a
    GET /api/config/job-templates endpoint is added.
  - "Fetch Models" in Settings UI is non-functional from 043 until Spec 044
    adds GET /api/config/models and re-points the UI.
  - The job-templates.yaml ConfigMap must be mounted to the Job Controller pod
    (not the orchestrator). Changes to job-templates.yaml require a Job Controller
    rollout: kubectl rollout restart deployment/<release>-jobcontroller -n <namespace>

── Job Controller ────────────────────────────────────────────────────────────

Service: {{ include "coding-agent-automation.fullname" . }}-jobcontroller:{{ .Values.jobController.service.port }}
Leader election Lease: caa-{{ .Release.Name }}-dispatch-lock (in namespace {{ .Release.Namespace }})

Readiness check (run after deploy — must return 200 within 60 seconds):
  kubectl get pods -n {{ .Release.Namespace }} -l app.kubernetes.io/component=jobcontroller
  kubectl exec -n {{ .Release.Namespace }} <jobcontroller-pod> -- \
    curl -s -o /dev/null -w "%{http_code}" http://localhost:{{ .Values.jobController.service.port }}/readyz
  Expected: 200. If 503: leader election not yet complete, retry. If CrashLoopBackOff:
  check logs for fast-fail messages (missing PipelineApi:BaseUrl, AGENT_API_KEY, or not-in-cluster).

ATOMIC CUTOVER REQUIREMENT:
  The monolith's DispatchService is removed starting from this image tag. The Job
  Controller takes over dispatch. These TWO changes must ship in ONE helm upgrade:
    1. Updated monolith image (without DispatchService)
    2. jobController.enabled=true
  DO NOT enable the Job Controller against an old monolith image — both services
  would compete to claim WorkItems. The ClaimAsync 409 protects DB integrity, but
  a race at the wrong moment can produce a duplicate K8s Job.

IMMUTABLE IMAGE TAGS:
  Use semver or SHA tags — NOT the mutable "coding-agent-webui" latest tag.
  A mutable tag means helm rollback will NOT restore the old image, only values.

ROLLBACK PROCEDURE (if upgrade fails):
  1. helm rollback {{ .Release.Name }} <previous-revision>
     (restores jobController.enabled=false and old monolith image tag)
  2. Verify Job Controller Deployment deleted:
       kubectl get deployment -n {{ .Release.Namespace }} | grep jobcontroller
  3. Verify DispatchService logs in monolith:
       kubectl logs -n {{ .Release.Namespace }} deployment/{{ include "coding-agent-automation.fullname" . }}-orchestrator | grep DispatchService
  4. Check for orphaned WorkItems stuck in Dispatched state (claimed before crash):
       GET /api/work-items/active?olderThanSeconds=0
     Manually requeue via POST /api/work-items/{id}/requeue, or wait 120s for the
     monolith's ReconciliationService short-circuit sweep to recover them.

Job-templates ConfigMap changes require a Job Controller rollout to take effect
(templates are loaded once at startup):
  kubectl rollout restart deployment/{{ include "coding-agent-automation.fullname" . }}-jobcontroller -n {{ .Release.Namespace }}

## Pipeline API (api.enabled=true)

**api.replicas must remain 1.**
The SignalR Redis backplane (signalr.redis.enabled) enables hub message delivery across
replicas but does NOT make multiple API replicas safe. AgentRegistryService,
OrchestratorRunService, and all in-memory locking state are per-process singletons.
Do NOT scale to replicas > 1 before Spec 045 completes its concurrency model rewrite.

**Expected restarts during schema upgrades (Req 9.5b).**
When the orchestrator is applying database migrations, the API pod will repeatedly log:
  "Database has N pending migration(s)" (Error level)
and restart with backoff until the migration completes. This is normal and self-resolving.
Do NOT roll back on seeing these restarts — the API automatically recovers once the
orchestrator finishes. Migration duration varies by schema change, typically 1–3 minutes.
